# MCP Media Generator

خادم **MCP لتوليد الوسائط** يجمع أربع قدرات في أداة واحدة:
1. **توليد صور** من وصف نصي — `gpt-image-2-6/flare-text-to-image`
2. **توليد فيديو بصوت متزامن أصلي** — `grok-imagine-video-1-5-preview` (image-to-video اختياري)
3. **دمج عدة مقاطع فيديو** في مقطع واحد عالي الجودة — عبر خدمة `video-merger` المرفقة
4. **تحويل 4–8 صور إلى فيديو رأسي 9:16 بتحريك خفيف** (مقطع 15 ثانية لكل صورة + دمج نهائي) — عبر ffmpeg داخل خدمة الدمج، **بلا أي API مدفوع**

تطبيق **Next.js واحد** (App Router + TypeScript + Tailwind) فيه:
- **خادم MCP** على المسار `/mcp` (نقل Streamable HTTP عبر SDK الرسمي `@modelcontextprotocol/sdk`) يعرض **6 أدوات**، والنتائج تُصاغ بالعربية.
- **واجهة عربية RTL** لإدارة مفاتيح API ومتابعة المهام حية وإعدادات الربط جاهزة للنسخ لأي عميل MCP.
- **صفحة رفع صور `/images-to-video`**: اسحب 4–8 صور، رتّبها، اختر مدة المقطع (5–20 ثانية)، وشاهد التقدم مرحلة بمرحلة حتى فيديو MP4 جاهز للتنزيل.

## القواعد الجوهرية المنفذة

| القاعدة | التنفيذ |
|---|---|
| روابط فقط | لا يُنزَّل أي ملف وسائط على السيرفر — روابط النتائج فقط في قاعدة البيانات |
| ترتيب تسلسلي صارم | المفاتيح تُجرَّب بترتيب الإضافة (`created_at ASC, id ASC` بدقة مللي ثانية) — لا round-robin |
| لا توقف عند نفاد الرصيد | تبديل فوري للمفتاح التالي، ونفس المهمة تُستأنف بنفس `task_id` |
| العميل لا يرى أخطاء المفاتيح | التبديل صامت تمامًا — لا رسالة تخرج للعميل تذكر مفتاحًا أو رصيدًا |
| فشل على كل المفاتيح | المهمة تبقى `processing` وتُعاد تلقائيًا مع كل `get_task` بعد تهدئة ~45 ثانية |
| الدمج الحتمي | أخطاء خدمة الدمج المعلنة (4xx/5xx) فشل نهائي فوري — أخطاء شبكتنا مؤقتة |
| إخفاء المفاتيح | `maskKey` في كل الاستجابات والسجلات: أول 7 + `••••••••` + آخر 4 |
| 24 ساعة للدمج | التحذير مذكور في وصف الأداة وفي SERVER_INSTRUCTIONS وفي رد الاكتمال |

## الأدوات الست على `/mcp`

| الأداة | الوظيفة |
|---|---|
| `generate_image` | توليد صورة — تعيد الرابط مباشرة إن اكتملت خلال نافذة الانتظار وإلا `task_id` |
| `generate_video` | توليد فيديو بصوت متزامن — `task_id` فوري مع بث تقدم حي |
| `merge_videos` | دمج 2–10 مقاطع بالترتيب — بـ `urls` مباشرة أو `task_ids` لمهام مكتملة |
| `images_to_video` | تحويل 4–8 صور إلى فيديو واحد رأسي 9:16 — بـ `images` روابط مباشرة أو `task_ids` لمهام صور مكتملة؛ مقطع `clip_seconds` (5–20، افتراضي 15) لكل صورة بتحريك خفيف Ken Burns ثم دمج `-c copy` — بلا أي API مدفوع |
| `get_task` | تتبع أي مهمة — يحدّث الحالة حية من المزود أو خدمة الدمج، ويقود خطوات العرض الصوري المتبقية |
| `list_media` | استرجاع أحدث الوسائط المخزنة بروابطها (image / video / merge / slideshow) |

أثناء الانتظار يُبث **Progress notifications** كل ~3 ثوانٍ إذا زوّد العميل الطلب بـ `_meta.progressToken` (وضع SSE فعلي عبر Streamable HTTP).

## التشغيل المحلي

```bash
bun install
# أنشئ .env.local (انظر .env.example) ثم:
bun run dev          # خادم التطوير على :3000

# خدمة الدمج (مجلد مستقل يحاكي Vercel):
cd mini-services/video-merger && bun install && node server.js   # على :4000
```

ثم اضبط في الواجهة مفتاحًا واحدًا على الأقل لكل مزود، واربط أي عميل MCP بالرابط `http://<origin>/mcp`.

```bash
# وحدات طبقة المشروع (تصنيف الأخطاء، إخفاء المفاتيح، توحيد الموديلات):
bun run scripts/test-unit.ts                          # 27/27

# e2e كامل عبر MCP (مزود kie وهمي + دمج حقيقي بفيديوهين عامين):
# 1) أزل التعليق عن KIE_API_BASE=http://127.0.0.1:4600 في .env.local (وانتظر إعادة تحميل الخادم)

node scripts/mock-kie.mjs &
node scripts/mcp-e2e.mjs                              # 42/42
# يتطلب أيضًا خدمة الدمج تعمل على :4000

# اختبار المزود الوهمي وحده (يحاكي Jobs API الموحد بأشكال kie الحقيقية):

```

نتائج الفحص المسجلة في هذه البيئة:
- `bunx tsc --noEmit` — نظيف بلا أخطاء.
- `next build` — ينجح (تم فحصه بمجلد بناء منفصل: `NEXT_DIST_DIR=.next-prodcheck bunx next build`).
- `GET /api/health` — `ok:true` + `database:"turso-connected"` + `merger.healthy:true`.
- e2e: تهيئة MCP، مخططات الأدوات الخمس مطابقة حرفيًا، تبديل تسلسلي (سيء ← مستنزف ← صحيح) يكتمل على الثالث دون أي ذكر للمفاتيح، تتبع get_task حتى روابط فعلية، دمج حقيقي بفيديوهين عامين بدقتين مختلفتين → MP4 بـ 1280×720 يعمل مع Range 206، رفض 1/11 مقطعًا برسائل عربية، list_media مرتبة من الأحدث، تنظيف كامل لآثار الاختبار.
- ميزة العرض الصوري: e2e كامل لخدمة الدمج (6 صور → 6 مقاطع 15 ثانية → فيديو 90 ثانية 720×1280 @ 24fps) + أداة `images_to_video` عبر `/mcp` (19/19) + تدفق الواجهة بالمتصفح من الرفع حتى رابط التنزيل.
- اختبارات خدمة الدمج: 16/16 وحدات + 28/28 HTTP (انظر README الخاص بها).

## متغيرات البيئة (Vercel → Settings → Environment Variables)

| المتغير | إلزامي | الوصف |
|---|---|---|
| `TURSO_DATABASE_URL` | نعم | `libsql://<db>-<org>.turso.io` |
| `TURSO_AUTH_TOKEN` | نعم | توكن Turso بصلاحيات كتابة |
| `MERGER_API_BASE` | نعم | رابط نشر خدمة الدمج (مجلد `mini-services/video-merger`) |
| `MCP_ACCESS_TOKEN` | لا | إن ضُبط يُطلب `Authorization: Bearer <token>` على `/mcp` |
| `KIE_IMAGE_MODEL` / `KIE_VIDEO_MODEL` | لا | تجاوز أسماء الموديلات لدى kie |
| `COMETAPI_IMAGE_MODEL` / `COMETAPI_VIDEO_MODEL` | لا | تجاوز أسماء الموديلات لدى CometAPI |
| `KIE_API_BASE` / `COMETAPI_API_BASE` | لا | روابط أساس المزودين — للاختبار فقط، احذفها في الإنتاج |

## النشر على Vercel (خطوتان)

1. **خدمة الدمج أولًا**: انشر `mini-services/video-merger` كمشروع Vercel مستقل (README الخاص بها) وانسخ رابطه العام.
2. **هذا المشروع**: اربط المستودع بـ Vercel وأضف المتغيرات أعلاه (مع `MERGER_API_BASE=رابط خدمة الدمج`) → Deploy. كل شيء يعمل عبر HTTP بلا أي ملف محلي.

> ملاحظات نشر: مسار `/mcp` يستخدم وضع **stateless** (جلسة جديدة لكل طلب) للتوافق مع serverless؛ نافذة الانتظار حتى 240 ثانية تتطلب `maxDuration` ≥ 300 (خطة Pro على Vercel — على Hobby حدّد `wait_seconds` ≤ 55). لا تُرفع أي أسرار إلى Git — `.env*` مستثنى منذ أول commit.
